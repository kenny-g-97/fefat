# Research: embedding a Claude agent (Anthropic surfaces, as of 2026-10-05)

> Provenance: research by a Claude subagent on 2026-10-05 from Anthropic's platform docs, the Claude Agent SDK docs, and the Claude API reference bundled with Claude Code. Facts are cited; items marked **Inference** are the researcher's judgment.
>
> How FEFAT uses this: the masterplan chose the **Messages API tool loop** (option a below) because FEFAT is a local-first desktop product that must run on Windows and macOS with the customer's own API key. The Agent SDK (option c) and Managed Agents (option b) remain documented here as the alternatives behind the `AgentRuntime` seam. See `04-agent.md`.

## Agent SDK deployment requirements

- **Runtime:** Python 3.10+ or Node.js 18+. Both packages bundle the native Claude Code binary, except some installs (for example `npm ci --omit=optional`).
- **Process model:** each session is one `claude` subprocess that owns a shell, a working directory and the transcript file.
- **Sizing and network:** start at 1 GiB RAM, 5 GiB disk and 1 CPU per agent; needs outbound HTTPS to `api.anthropic.com`.
- **Session patterns:** ephemeral (one container per task); long-running (TypeScript `streamInput()` / `startup()`, Python `ClaudeSDKClient`); hybrid (containers spin down between visits; a `SessionStore` is required); multi-agent container; route each session to the same container by hashing `sessionId`.
- **Isolation options:** sandbox-runtime (bubblewrap on Linux, Seatbelt on macOS), hardened Docker (`--cap-drop ALL`, `--read-only`, `--network none` plus a Unix-socket proxy), gVisor or Firecracker. The cookbook covers Docker, Modal and Kubernetes.
- **Per-tenant isolation:** give each tenant its own `cwd` and `CLAUDE_CONFIG_DIR`, set `settingSources: []` and `CLAUDE_CODE_DISABLE_AUTO_MEMORY=1`, and apply per-tenant egress rules. The docs say "Do not rely on default `query()` options for multi-tenant isolation".

## Data handling notes

- **Files API scope:** uploaded files are visible to the whole workspace, not to one end user. The docs say "Never accept `file_id` values from end users" and suggest one workspace per tenant, with a limit of 100 workspaces per org.
- **Self-hosted Managed Agents:** your filesystem stays on your hosts, but tool inputs and outputs still reach Anthropic's control plane, and skills and memory stores are stored by Anthropic.
- **Conflicting retention wording:** the API retention page says conversation content is not retained by default. The Claude Code data page says "Standard: 30-day retention" for API users. Confirm with Anthropic which one applies to Agent SDK traffic.

## Recommendation from the research (Inference)

**Single user, self-hosted infrastructure: Agent SDK.** Strategy files, data and the backtester already live in your infrastructure, so the agent edits files in place; `canUseTool` gives a diff-approval hook; Skills are folders in your repo; no beta label; pay only tokens plus one container. Set `permissionMode:"default"` explicitly; never allowlist Write, Edit or Bash; use a Postgres `SessionStore` for cross-device resume; relay `stream_event` messages to clients; use `defer` for approvals answered later.

**Multi-tenant SaaS: Managed Agents as the primary candidate, with conditions:** beta; not ZDR/HIPAA eligible; you keep the mapping between users and file IDs; set `limited` networking explicitly.

**Either way:** build FEFAT's tools once behind a neutral interface (read file, propose edit, register feature, query backtest, create strategy version, run backtest). That keeps a later move between options cheap.

**FEFAT's final choice (made after this research):** the product is local-first and must run natively on Windows; the Python Agent SDK has no Windows wheel, and the Messages API loop is pure Python, GA, and works with the customer's own key. So the masterplan builds (a) and keeps (c) as an alternative.

## Pitfalls the docs call out

1. **Preserved thinking (append-only history).** On Opus 5.5, Sonnet 5.5 and Fable 5.1, each thinking block is tied to the exact `system` prompt, `tools` list and earlier messages it was produced with. For accounts created on or after 2026-08-31, replaying an edited history returns a 400. Managed Agents and the Agent SDK keep this prefix intact automatically. A hand-built Messages loop must: freeze the rendered system prompt; add or remove tools only via `tool_addition` / `tool_removal` (beta `mid-conversation-tool-changes-2026-07-01`); use server-side compaction instead of rewriting history.
2. **Forced tool choice removed.** `tool_choice` `any` or `tool` returns a 400 on these models. Use `auto` plus `strict: true` and a prompt instruction, then check that a tool call actually happened.
3. **Thinking behaviour changes.** Opus 5.5: thinking cannot be turned off, default effort is `medium`, and `max_tokens` needs room for thinking (about 64K for agentic coding). The short notes the model writes between tool calls arrive as empty `thinking` blocks unless you set `thinking.display:"updates"` (beta `thinking-display-updates-2026-08-18`); otherwise the UI goes quiet during long turns. Sonnet 5.5: `thinking: disabled` returns a 400; use `between_tools` instead.
4. **Refusals.** A refusal comes back as HTTP 200 with `stop_reason:"refusal"` (Opus 5.5 categories include `cyber`, `bio`, `reasoning_extraction`). Never run tools from a refused turn. Opt in to `fallbacks:"default"` (beta `server-side-fallback-2026-07-01`). The fallback model cannot read Opus 5.5's thinking blocks.
5. **Beta headers.** Never send both `managed-agents-2026-04-01` and `agent-memory-2026-07-22` on a memory-store call. `files.list(scope_id)` needs the managed-agents beta passed explicitly.
6. **Managed Agents defaults.** Create each agent once; built-in tools default to `always_allow`; `auto` "is not a human checkpoint"; environments created through the API default to `unrestricted` networking; only stop reading the stream when the session is idle with a stop reason other than `requires_action`.
7. **Agent SDK gotchas.** `canUseTool` never fires for calls that are already auto-approved; if you omit `permissionMode`, the session may start in `auto` mode (TypeScript v0.3.286 and later); use `PreToolUse` hooks for checks that must always run; checkpointing ignores edits made through Bash or by subagents; `SessionStore` writes are best-effort (watch for `mirror_error`); the `env` option replaces the subprocess environment in TypeScript but merges into it in Python; `total_cost_usd` is an estimate; `AskUserQuestion` is not available inside subagents.
8. **Tool Runner.** The Python runner does not auto-resume after `pause_turn`. TypeScript/Ruby client-side compaction is deprecated in favour of server-side compaction.
9. **Licensing and authentication.** Third-party products may not offer claude.ai login or route requests through Free/Pro/Max credentials. The legal page says running Claude Code in your products comes with the condition "Customers may not pay for, resell, or intermediate Claude usage on their end users' behalf", while the SDK overview says the Commercial Terms cover SDK use "including when you use it to power products and services that you make available to your own customers". Get written confirmation before launching a multi-tenant Agent SDK product on your own API key. (Not a concern for a Messages-API product where customers use their own keys.)

**Where the bundled reference and live docs disagreed (live used):** Managed Agents file resources per session (999 vs 500); mount path (`/workspace/…` vs `/mnt/session/uploads/…`); rate limits; skills per agent (20) vs per session (500); Files API storage (100 GB vs 1 TB per org); code execution `pip install` at runtime (bundle) vs no internet (live); Tool Runner approval gates inside the runner (bundle) vs manual loop recommended (live).
