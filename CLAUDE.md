# FEFAT — working agreements

FEFAT ("feature engineering for algorithmic trading") is a local-first research platform for futures and crypto traders: a feature lab, a Rust backtesting engine with strict versioning, a prop-firm simulator, an in-app Claude agent, and phone access. It is built step by step from the masterplan: start at [docs/masterplan/README.md](docs/masterplan/README.md). How a step runs is in [05-build-process.md](docs/masterplan/05-build-process.md); how code is shaped is in [08-code-design.md](docs/masterplan/08-code-design.md).

This file holds what every session needs. Language conventions live in `.claude/rules/` (loaded by path), procedures in `.claude/skills/`, architecture in the docs, and the hard limits in the hooks under `.claude/hooks/`, registered in `.claude/settings.json`.

## Repository map

- `engine/`: the Cargo workspace. `fefat-core` holds the types and the `MarketDataReader` trait, with no I/O; `fefat-engine`, `fefat-prop`, and `fefat-metrics` are pure computation; `fefat-data` is the only crate that opens files; `fefat-py` builds the Python module `fefat_engine`; `fefat-cli` drives goldens and benchmarks.
- `python/fefat/src/fefat/`: the SDK (`import fefat as ff`), with `market`, `features`, `indicators`, `strategy`, `backtest`, `prop`, `analytics`, `research`, and `reference`.
- `python/fefat_app/src/fefat_app/`: the local server, with `http/`, `services/`, `ports.py`, `container.py`, and the adapters (`database/`, `jobs/`, `executor.py`, `agent/`, `push/`, `credentials.py`).
- `python/tests/`: pytest for both packages.
- `web/`: the Vite, React, and TypeScript app (pnpm), organised by product area; its design system is `web/DESIGN.md` (from step 4.3).
- `fixtures/synthetic/`: market data generated by `scripts/gen_fixtures.py` and listed with seed and SHA-256 in its `MANIFEST.json`, the only data files in git. `fixtures/scenarios/`: the fill-rule scenario tables. `fixtures/goldens/`: golden runs (from Phase 2).
- `notebooks/`: demos and checks, committed without outputs.
- `scripts/`: `doctor.py`, `masterplan_step.py` (reads steps for `/step` and the session hook), `test_hooks.py`, `gen_fixtures.py` (the synthetic fixtures), `guard_data.py` (the commit guard), and `strip_notebooks.py`.
- `docs/masterplan/`: the plan with `PROGRESS.md`, `BACKLOG.md`, and `DECISIONS.md`. [docs/adr/](docs/adr/): a record for each decision the log marks ADR. `docs/spec/`: normative specifications.
- `.github/`: the pull request template (and the CI workflow from step 0.6).
- `.claude/`: `settings.json`, `hooks/`, `rules/`, `skills/`, `agents/`. `.githooks/pre-commit` and `pre-push`: the commit gate and the push gate (both run `scripts/guard_data.py`, the second over each commit a push sends), active once `just setup` has set `core.hooksPath` in the clone.

## Commands

The same in PowerShell, Git Bash, CI, and macOS:

```text
just doctor   # the tools FEFAT needs, each OK or MISSING
just setup    # the commit gate, uv workspace, Cargo workspace, web dependencies, the engine build
just check    # the data guard, ruff, pyright, import-linter, cargo fmt and clippy, oxlint, tsc
just test     # the engine build, then pytest, the hook smoke tests, cargo test, vitest
just build-engine  # compile the engine into .venv, where `import fefat` finds it
just strip-notebooks  # clear notebook outputs; then git add the notebooks again
just gen-schema  # write the StrategySpec JSON schema from the Rust types; a cargo test fails when it is stale
just dev      # local server and web dev server (from Phase 4)
```

`just e2e` and `just up` arrive with Phases 4 and 5. Single checks: `uv run python scripts/test_hooks.py`, `uv run python docs/masterplan/tools/check_masterplan.py`, and `uv run --no-project python scripts/masterplan_step.py next` for where the plan stands.

## How work happens

- One masterplan step per session, run by the `step` skill: the builder starts it with `/step N.M` or in plain words ("0.6 is merged, plan the next step"), and `--dry-run` only previews it. A phase opens with `/phase-kickoff N` and closes with `/phase-exit N`.
- Every step works on a branch `step/N.M-<slug>` and ends with a pull request from `.github/pull_request_template.md`. Never commit to `main`: the builder squash-merges with the routine in `05-build-process.md` §8.
- GitHub's free plan cannot protect `main` (D-30), so the hooks and the merge routine are the only guard: never work around them.
- `git push`, `gh pr merge`, golden regeneration, new dependencies, and anything mentioning Databento always ask the builder first (`.claude/settings.json`).
- The builder plans every step in plan mode, whatever its meta line says: `Plan mode: required` makes the plan mandatory, and `skip` asks for a short one.
- Plans run on the strongest model (Fable) and the work on Opus: after approving a plan the builder switches with `/model opus` and says "proceed with opus"; continue the approved plan from its first item, without planning again. `Model hint: hard` marks the steps where the strongest model matters most.
- Stay inside the step and put anything else in `docs/masterplan/BACKLOG.md`. If a step's assumption no longer holds, stop and propose an Amendment block instead of deviating silently.
- A plan revision or setup change the builder asks for during a step (a skill, reviewer, plugin, or setting) goes in its own commit before the step's work, or its own `config/<slug>` pull request when it stands alone, with a `DECISIONS.md` entry when it decides something. The builder merges that pull request before the step's opens: two pull requests never wait on each other.
- A step's closing message names the next step and the line to type in a fresh session (`/step N.M`, or `/phase-exit N`): the builder asks after every merge.
- When an option costs money, recommend the free or local one first and give the paid one's monthly cost (D-01, D-30).
- Each acceptance item gets a test that fails without the change, shown failing first.
- Before the pull request: `just check`, `just test`, the `verify` skill, the `step-reviewer` subagent, `/code-review`, `/ponytail-review` (the ponytail plugin, D-32), the reviewers on the step's meta line, and `/security-review` when it says `Security: yes`.
- The pull request writes the step's `PROGRESS.md` row as `done` with its number; the row becomes true when it is merged.
- After an interruption, resume from git, the step file, and `PROGRESS.md`, not from memory; the session-start hook prints where the work stands.
- Commits have an imperative subject under 72 characters ending in `(step N.M)` (on kickoff and exit branches, `(Phase N kickoff)` or `(Phase N exit)`), and a body that says why.

## Invariants

Each is a decision in `docs/masterplan/DECISIONS.md`, with its record where it has one.

- Runs are deterministic, pinned, and hashed; versions and runs are immutable (D-11, [ADR-0009](docs/adr/0009-deterministic-pinned-hashed-runs.md)).
- No look-ahead: features are prefix-invariant and pass the leak detector (D-12, [ADR-0010](docs/adr/0010-leak-detector-prefix-invariance.md)).
- Licensed market data never enters the repository, a pull request, or a prompt, and FEFAT ships none: traders connect their own sources (D-21; D-37, [ADR-0018](docs/adr/0018-own-data-sources-no-shipped-data.md)).
- Scenario tables specify the fills, and the Python reference engine is the oracle the Rust engine matches exactly (D-07, [ADR-0005](docs/adr/0005-bar-close-decisions-finest-data-fills.md); D-10, [ADR-0008](docs/adr/0008-fill-spec-scenarios-reference-engine.md)).
- Goldens change only with the builder's approval, a fill-model version bump when fills change, and a changelog entry (the `engine-golden` skill).
- Tests are never weakened, skipped, or deleted to make them pass.
- Dependencies point inward, `web → fefat_app.http → services → fefat → fefat_engine`, and a new dependency needs an ADR line (D-27, [ADR-0016](docs/adr/0016-modular-monolith-ports-and-adapters.md), `08-code-design.md` §1).

## Code design, skills, and reviewers

- The SDK is the core; everything that touches the outside world is an adapter behind a named port (`fefat_app/ports.py`, and the `MarketDataReader` and `AccountModel` traits in Rust), built once and injected (D-27).
- Intention-revealing names from the glossary in `00-product-spec.md` §7 (never `data`, `utils`, `helpers`, `manager`), fail-fast errors that say "Expected …, got …", an enum for every state, injected dependencies, immutable values, and small units (`08-code-design.md` §3).
- Skills per area, which the `step` skill loads: `software-design-principles` for any code; `designing-architecture` for a new module, package, crate, or seam; `backtest-expert` for engine, prop, results, and research work; `frontend-design:frontend-design` with `web/DESIGN.md` for anything under `web/`; the bundled `claude-api` skill for any code that calls the Anthropic API.
- Read-only reviewer subagents: `step-reviewer` for every step; `engine-accuracy-reviewer` for engine, data, and prop steps; `leakage-auditor` for feature, data, and research steps; `ui-verifier` for UI steps (from step 4.3); `design-reviewer`, with the `apple-design` skill, for UI steps (from step 4.3) and the exits of phases with UI (D-34).
- Code reviewers on every branch and every phase diff: `/code-review` for correctness, and the ponytail plugin's `/ponytail-review` for code that need not exist, besides bugs, safety, load, tests, and speed (D-32; installed per machine, `06-claude-code-setup.md` §7).

## This machine

- Native Windows 11 (no WSL for this project). PowerShell and Git Bash are both available.
- Bare `python` and `python3` are Microsoft Store stubs here: always run Python through `uv run python` (or `python3.12`).
- Line endings are LF everywhere (`.gitattributes`, `.editorconfig`); use `pathlib` for paths.
- `just` runs recipe lines in `cmd.exe` on Windows, so a recipe line is one plain command: no `&&`, pipes, or environment prefixes.
- Node 24 runs the Claude Code hooks. The settings call them in exec form (`node` and its arguments), never through a shell, and their smoke tests are `scripts/test_hooks.py`.
- The standalone `claude` CLI is not installed, by choice: Claude Code runs in the VS Code extension, plugins come from `/plugins`, and the extension's own CLI sits in `~/.vscode/extensions/anthropic.claude-code-*/resources/native-binary/`.
- The language-server plugins (`rust-analyzer-lsp`, `pyright-lsp`, `typescript-lsp`) report type errors after each edit; their servers must be on PATH (`06-claude-code-setup.md` §7).
- The builder knows Python and notebooks well and is new to web, mobile, and DevOps: explain those parts plainly, say in plain words what a step changes in their store and why, and prefer checks they can run or click over code they must read.

## Never

- Commit, attach, or paste licensed market data. Real data lives outside the repository under `FEFAT_DATA_DIR` and is referenced by path only: code gets the folder from `fefat.config.resolve_paths` (default `<FEFAT_HOME>/data`), never from a hard-coded path. Only generated fixtures under `fixtures/synthetic/` are committed, and the commit guard refuses market-data files anywhere else (binary formats, archives, CSV and other text tables of prices, under any name), fixtures missing from their manifest, files over 25 MB, secrets, and notebooks with outputs, in every commit a push sends as well. Read aggregates (counts, statistics, a few sample rows) into the conversation, never raw data.
- Commit secrets (`.env*`, API keys, certificates). Keys go in the operating system's credential store.
- Weaken, skip, or delete a test to make it pass, or change a scenario's expected value to match the code.
- Commit on or push to `main`, force-push, pass `--no-verify`, or change `core.hooksPath`. The shell hook refuses all of these except the commit on `main`, before which it asks.
- Merge a pull request: the builder merges, after running the step's checks.
